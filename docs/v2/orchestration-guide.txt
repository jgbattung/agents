# Orca orchestration

If your prompt has a preamble with Task and Dispatch IDs, you are a worker:
follow the preamble. To ask your coordinator, run `ask`, then end your turn;
Orca wakes you with the answer. To hand work off with nothing back, use `orca-cli`.
When you report your effort, take it from the dispatch's `--effort` or your process
argv, not from a numeric `reasoning_effort`: that number is not on a 0–100 scale
(claude-opus-5-5: low=5, medium=10, high=15, xhigh=40).

## Recipe

`ORCA` stands for the executable you used to run `skills get`; type it in its
place and use it for every command.

Write multiline text to a file with your file tool, then pass that file: --body-file, --spec-file, git commit -F, gh ... --body-file.
Never use heredocs (<<) or here-strings (<<<); they can hang the shell.
If send, reply or worker-start fails, do only what the CLI prints and keep that file unchanged. Never retry on your own or with a new ID.

```text
ORCA orchestration worker-start --environment local --spec "<task>" --worktree current --agent <agent>
```

`--environment local` keeps a command on this machine's Orca whatever
`ORCA_ENVIRONMENT` or a pairing code in your shell selects. Put it on every
start you mean to run here, and on the commands that create or list that
Run's Tasks and workers (`run-create`, `task-create`, `task-list`,
`worker-list`) so they reach the same Orca; a start on a paired server takes
`--on <server>` instead.

`<agent>` is an Orca agent id: one the user named, else the agent you are
running as when the worker shares your execution host. Otherwise, such as a
different SSH/WSL host or `--on`, ask the user. `worker-start` does not check
that the CLI is installed; a missing one fails as an `agent_readiness` timeout.

- Start independent workers at the same time, up to about 4 at once, and
  start the rest as those return. Separate tool calls often run one after
  another, so start each group from one shell command: load
  `references/parallel-start.md` for the POSIX and PowerShell forms.
  Then **end your turn**. "Report back" and
  "tell me when it's done" still mean end your turn; Orca wakes you and you
  report then.
- If a receipt has `next`, follow it. When Orca has nothing for you, end your
  turn.
- `--worktree current` uses your workspace. Use a new one only when the user
  asks or sharing would conflict: `--worktree new-child --name <short-name>`
  nests it under yours. For one with no parent, use
  `--worktree new-top-level --repo id:<repoId> --name <short-name>`
  (`ORCA repo list --json` gives the id). If nothing needs to come back to you
  (the user will work in those chats), don't start workers; per workspace run
  `ORCA worktree create --name <name> --no-parent --agent <agent> --prompt "<brief>" --json`
  and end your turn.
- Pick the machine before you start when the user named another machine for
  this project, now or earlier in this Run, when the work is for another
  project, or when your workspace has no project: load
  `references/placement-and-remote.md` ("Which machine"). Otherwise your
  current workspace's project runs where you are, with no host check.
- Add `--model` only if the user named one.
- If `worker-start` fails, do not rerun it; read `failedStage` and load
  `references/recovery-and-cleanup.md`.
- To talk to a worker, use
  `ORCA orchestration send --to dispatch:<dispatch_id> --subject "<topic>" --body "<message>"`
  in any state: a working worker gets it when its current turn ends; a finished
  or closed one gets it as a follow-up Task and reports with `worker_done` (do
  not pass `--on` for a Dispatch follow-up). The receipt says which.
  If a legacy paired-server attachment refuses `send` with `dispatch_inactive`,
  start new work there with `worker-start --on <server>` (load
  `references/placement-and-remote.md` first).

Never:

- Poll or run watch scripts: a script's plain `check` takes your mail, so it is
  hidden from you and Orca has nothing to wake you with. Orca wakes you.
- Steer or read through a worker's terminal: a worker may be a chat with none.
  Use `send` to steer and
  `ORCA orchestration worker-read --dispatch <dispatch_id>` to read its recent
  output; both work for every worker.
- Make checkouts yourself; let `worker-start` create a worker's workspace.

## When Orca wakes you

- In a chat, each message arrives whole as its own message: act on it. A wake
  that names a `check` command (a terminal, or one message too large for a chat
  message) means run that command. Answer a `question` with
  `ORCA orchestration reply --id <message_id> --body "<answer>"` when the answer
  follows from the task or the user's instructions; otherwise ask the user first.
- An `escalation` with `stopReason` means the worker stopped without
  `worker_done`: for `lost`, inspect `worker-show` first - the original agent
  may still be running, and `unverifiable` liveness does not authorize sending
  mail or retrying (report the uncertainty instead); for `exited`, process exit
  is confirmed - stop if needed, then retry it or tell the user; for other stop
  reasons, steer it with `send`, stop and retry it, or tell the user.
- A `worker_done` settles its Task; never mark a reported failure completed.
- When every worker has settled, report to the user per Task: outcome,
  evidence, open blockers.
- Lost track? `ORCA orchestration inbox --terminal run:<run_id> --limit 50`
  shows mail `check` already handled.

Finished workers close on their own unless `worker-list` gives one a `next`; follow
it. Kept-open workers, including new-workspace ones, stay open for the user.
A closing worker also closes the setup terminal and startup tabs its start opened,
and terminals it created without `--keep-open` (workers started before this version,
or on a legacy paired host, have none); a failed setup stays open.
`send` reopens a closed worker when you need it again.
Start a worker in your workspace with `--keep-open` when the user will keep using
its chat after it reports: they want to watch it or talk to it. To keep one already
started, run
`ORCA orchestration worker-keep-open --dispatch <dispatch_id>`.

## Task spec

Make each spec self-contained: the target, the change, constraints, what the
worker may edit, and the evidence that proves it is done. Say what the
deliverable is. A failing command or check the worker runs is a result to
report (succeeded), not a failed Task, unless it keeps the worker from
finishing. A Task that succeeds unblocks its dependents even when its report
lists problems; if a later Task should start only on good results, start it
yourself after reading the report instead of making it depend on this one.
Send fixes to a worker unless the user gave them to you.

If the user said which machine to use, this one ("here") included, or "Which
machine" picked it, a new Task's spec ends with a second line, either a line
break inside the quotes or the last line of a `--spec-file`:

```text
--spec "<task>
Placement: <machine name> (<kind> <id>), <reason>."
```

This machine is `this machine (local)`; a reason is `the user named it`.

Fetch this guide once. Summarize the worker's evidence; rerun checks only for a
gap or contradiction.

## Safety

Silence, a timeout, or `unverifiable` liveness alone never proves exit or authorizes
autonomous recovery. For explicit user cancellation or assignment abandonment,
load `references/recovery-and-cleanup.md`: requesting a guarded stop or fencing an
assignment does not prove its agent stopped.

# Coordinator loop

## Task DAGs

A Task needs a Run, so create one first. Workers editing the same files at once
need separate workspaces.

```text
ORCA orchestration run-create --environment local --objective "<goal>"
ORCA orchestration task-create --environment local --spec "<dependent work>" --deps <json_array>
ORCA orchestration task-list --environment local --ready --brief
ORCA orchestration worker-start --environment local --task <task_id> --worktree current --agent <agent>
```

On every wake, start the Tasks `task-list --ready` shows.

## Several Runs

A later `run-create` keeps your earlier Runs: their mail still wakes you, but
commands without `--run` use the newest Run, so pass `--run <id>` for an earlier
one. `run-use` keeps only the Run it names.

# Low-level topology

```text
ORCA terminal create --worktree active --title <task_name> --command "<agent_command>" --json
ORCA terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000 --json
ORCA orchestration dispatch --task <task_id> --to <handle> --inject
```

To give a Task to a terminal or chat Orca did not start:

```text
ORCA orchestration worker-start --task <task_id> --terminal <handle> --json
```

# Messaging and gates

Handle a whole `check` batch before the next `check`.

Groups (`@all`, `@idle`, `@codex`, ...) reach the live workers of your Run;
`@worktree:<id>` also reaches coordinators in that workspace. Use groups only
for deliberate fan-out.

To reach an agent on a paired server, use `send --on <server>`; a reply to mail
from another server needs no flag. See
[Placement and remote execution](placement-and-remote.md).

# Start independent workers in parallel

Each `worker-start` waits until its agent is ready (often about 10 seconds). Many agents run their
own tool calls one after another, so separate tool calls do not overlap. Start a group of up to
about 4 from one shell command instead, then start the rest as that group returns.

Rules:

- Put each spec in its own file and pass `--spec-file`, so no argument needs quoting.
- Give each start its own receipt file and error file, and collect each exit status.
- Read every receipt, including after a failure: a receipt with `next`, `failedStage` or recovery
  steps is handled exactly as for a single start. A missing or cut-off receipt is an unknown
  outcome: check `ORCA orchestration worker-list --environment local` before anything else, and
  never start that spec again blindly.
- Use the form for the shell that runs the CLI. `ORCA` stands for the executable path you resolved;
  quote it if it contains spaces.

POSIX shells (bash, zsh; also WSL and SSH hosts):

```sh
d=$(mktemp -d)
ORCA orchestration worker-start --environment local --spec-file w1.md --worktree new-child --name w1 --agent <agent> >"$d/w1.out" 2>"$d/w1.err" & p1=$!
ORCA orchestration worker-start --environment local --spec-file w2.md --worktree new-child --name w2 --agent <agent> >"$d/w2.out" 2>"$d/w2.err" & p2=$!
s=0; wait "$p1" || s=$?; echo "w1 exit $s"
s=0; wait "$p2" || s=$?; echo "w2 exit $s"
for f in "$d"/*; do echo "== $f"; cat "$f"; done
```

Windows PowerShell (5.1 or later; from cmd, run `powershell -NoProfile -Command` with this):

```powershell
$d = New-Item -ItemType Directory -Path (Join-Path $env:TEMP ([guid]::NewGuid()))
$starts = foreach ($n in 'w1', 'w2') {
  $p = Start-Process -FilePath 'ORCA' -NoNewWindow -PassThru -WorkingDirectory (Get-Location) `
    -ArgumentList "orchestration worker-start --environment local --spec-file $n.md --worktree new-child --name $n --agent <agent>" `
    -RedirectStandardOutput "$d\$n.out" -RedirectStandardError "$d\$n.err"
  $null = $p.Handle
  [pscustomobject]@{ Name = $n; Process = $p }
}
foreach ($s in $starts) { $s.Process.WaitForExit(); "$($s.Name) exit $($s.Process.ExitCode)" }
Get-ChildItem $d | ForEach-Object { "== $($_.Name)"; Get-Content $_.FullName }
```

# Placement and remote execution

Folder workspaces are valid. `new-child` and `new-top-level` make Git worktrees,
never in a folder project; never `git init` a user's folder. From a multi-repo
folder workspace, `new-child` nests under the folder and needs `--repo` naming
the Git repo to create the worktree in.

Local `current`, `new-child` and `new-top-level` stay in the caller's project;
`new-child` also uses the caller's workspace as its parent. Omit `--repo` for
same-project Git work. Pass it for `new-child` or `new-top-level` from a folder
workspace, to deliberately target another project, or for connected-server
creation. The project visible in the app is not the caller's project. For
direct `worktree create`, likewise omit `--repo`/`--project` for same-project
work and use `--parent-worktree active` when requesting a child of the current
workspace.

```text
# Child of the current worktree.
ORCA orchestration worker-start --environment local --task <task_id> --worktree new-child --agent <agent> --setup run

# On a connected server, nested under your workspace; the Run stays on yours.
ORCA orchestration worker-start --task <task_id> --on <server> --worktree new-child --repo id:<repoId> --name <name> --agent <agent> --setup run

# On a connected server, with no parent.
ORCA orchestration worker-start --task <task_id> --on <server> --worktree new-top-level --repo id:<repoId> --name <name> --agent <agent> --setup run
```

With `--on`, both `new-child` and `new-top-level` need `--repo` naming a
project on that server: `id:<repoId>` from that server's `project setups` row
(see "Which machine" below). `new-child` nests the server's worktree under your
workspace on this machine. A server whose Orca is too old to nest across
machines still starts the worker, top-level, and the receipt's `warning` says
so; the worker is fine to use. `current` is not valid with `--on`.

`--name` is optional: without it Orca picks a name as it does for an unnamed
workspace, and the start output names the workspace it created.

After start, address a remote worker only by Dispatch ID, never by a terminal
handle.

## Which machine

Use this when the user named a machine for this project, now or earlier in
this Run, when the work is for another project, or from a workspace with no
project. Otherwise skip it: `current` and `new-child` already run where you
are.

Steps 1 to 4 choose where a new worktree goes. Work in an existing workspace
skips them, whatever its project's kind, a folder project included. Use your
own with `--worktree current`, or the one the user picked with its exact
worktree selector. Add `--environment local` here or `--on <server>` on a
server, and pass no `--repo`. If that selector does not resolve on that
machine, stop and tell the user. Then record it (step 5).

Only a coordinator places work on another machine. If you are a dispatched
worker, do not pass `--on`: ask your coordinator to place it.

1. Hosts. `ORCA host list --json`: `kind: local` is the machine your CLI runs
   on, `kind: environment` is a paired server (`--on <name>`, or its id when
   two servers share a name). A name the user gave that matches more than one
   row, such as an SSH target and a server, is not resolved: ask which.

2. Where the project is. A listing covers only the Orca that answers it, so ask
   each one, the servers together in one shell command:

   ```text
   ORCA project setups --environment local --json      # this machine
   ORCA project setups --environment <id> --json       # once per paired server
   ```

   `--environment local` pins a command to this machine whatever
   `ORCA_ENVIRONMENT` or a pairing code in your shell selects; without it, that
   read can be answered by a server and look like this machine's. `<id>` is the
   `id` of that server's `kind: environment` row. Do not add
   `--host runtime:<id>`: it drops the server's SSH rows. If `ORCA_PAIRING_CODE`
   or `ORCA_REMOTE_PAIRING` is set in your shell, unset it for the server reads.

   Match the project by `projectId` (such as `github:owner/repo`); a name must
   match one project id across every answer, or you ask. A `repo:<…>` id exists
   on one host only. A row is usable for a new worktree when `setupState` is
   `ready`, `repoId` is not empty, `kind` is not `folder`, and `hostId` is
   `local` (the machine that answered). Another `local` row is registered but
   not usable. A row with any other `hostId` describes an SSH target: a start
   cannot create a worktree there.

   Only a complete, successful list shows the project is absent on that
   machine. A server whose read fails is unchecked, with its reason:
   `remote_runtime_unavailable`, `runtime_timeout`,
   `runtime_environment_asleep`, `incompatible_runtime`, or a refused or
   cut-off answer. An `invalid_argument` about your selector is not an answer:
   fix the command first.

3. Decide. The first line that applies wins, and a line that says stop or ask
   ends the decision. A retry of an attempt that ran on a server is limited to
   two machines: that server and, once that attempt is settled, this one.
   Apply the lines to those two only. That attempt counts as your Run having
   placed the project on that server, and there you keep that attempt's repo.
   - The user named a machine, now or earlier in this Run for this project:
     use it, and the repo chosen with it. If that is no longer usable there,
     or the machine cannot be checked, stop and tell the user. Never
     substitute another machine or repo.
   - Your Run already placed this project, that machine and repo are still
     usable, and this machine has not become usable since: use the same
     machine and repo.
   - Usable on this machine: stay here, with `--environment local` and no
     `--on`.
   - Registered on this machine but not usable: stop and tell the user. Do not
     move it to a server.
   - Usable on exactly one paired server: start there with `--on`; do not wait
     for the user to name it.
   - Usable on several paired servers: ask the user once, naming each; keep
     the answer for the Run.
   - Usable nowhere, but registered somewhere (not ready, no checkout, or only
     on an SSH target): do not start it. Tell the user where it is registered
     and why it cannot be used.
   - Usable nowhere, and a server was unchecked: do not treat it as absent.
     Tell the user which servers you could not check and ask whether to go
     ahead here.
   - Registered nowhere, and every machine answered: place it as you would
     have without this section, and say in your report that no machine has it
     set up.

4. Selector. For a new worktree (`new-child` or `new-top-level`), take `repoId`
   from the chosen machine's own row and pass `--repo id:<repoId>`. Never reuse
   an id, path or name from another machine's row. If the user, or an earlier
   start in this Run, already chose a repo on that machine, use that exact repo
   while its row is still usable and do not ask again. Otherwise, with several
   usable rows there, use the one whose `path` or `displayName` the user named,
   else ask. Every start here carries `--environment local`, whichever line
   chose this machine; every start on a server carries `--on`.

5. Record it. For a new Task (`--spec`), write the task first, because the
   spec's first line becomes its title, then end the spec with a line of its
   own, either a line break inside the quotes or the last line of a
   `--spec-file`:

   ```text
   --spec "<task>
   Placement: <machine name> (<kind> <id>), <reason>."
   ```

   This machine is `this machine (local)`.

   `<reason>` is one of: the user named it; set up on this machine; the only
   ready candidate; the only known ready candidate (a server was unchecked);
   this Run already works there; no machine has it set up; the user chose to
   go ahead here with a server unchecked. Put what you checked on the other
   machines in your report to the user, not in the spec. An existing Task
   (`--task`, `--retry-of`) takes no new spec: give the machine, the reason and
   the new Dispatch ID in your report instead.

A worker on another machine has that machine's checkout, credentials and agents,
not yours. Push the branch or name the commit it needs; keep secrets, and paths
of files that exist only here, out of the spec. The listing cannot prove a
worker can start there. If the start is refused or the server does not answer,
report it; do not try another machine.

## Agents on another server

To message an agent that already runs on a paired server, send with `--on`,
using the same server names as `worker-start --on`:

```bash
ORCA orchestration send --on <server> --to <term_…|orca_session_id:…|bot:<name>> --type status|handoff|question|dispatch|merge_ready --subject "<text>" --body "<text>"
```

`--on` carries ordinary mail only. `escalation`, `decision_gate`, `worker_done`
and `heartbeat` belong to a Dispatch: send them without `--on`, from that
Dispatch, as you would on one computer.

A bot there takes only `status`, `handoff` or `question`, plus
`--chat <id|new>` and `--item <n>` as it does on its own computer, and treats
the request as its owner's.

Your own Orca carries the mail and keeps the conversation. Replies come back to
your own mailbox and wake you like local mail. The other agent answers
with a plain `reply --id <msg_id> --body <text>`; no flag is needed on either
side. Mail from another server names its sender as `<sender> on <server name>`.

`--environment <server>` runs one command on that server and delivers nothing back
to you, so an agent never mails with it. Your mailbox stays on your own Orca:
`check` takes no `--environment`. Read-only commands such as `inbox` or
`worker-list` with `--environment` show that server's records. A server whose Orca
is too old answers `server_mail_unsupported` and nothing is sent. Pair servers
with `orca pair` or in Settings.

# Recovery and cleanup

Act only on proof. `worker-list --run <run_id> --include-remote` gives
each worker's liveness and `next`; follow it.

Retry a failed or stopped attempt on the same Task; `--spec` would create a new
one. Placement is not inherited:

```text
ORCA orchestration worker-start --task <task_id> --retry-of <dispatch_id> --worktree <placement> --agent <agent>
```

An attempt that ran on a paired server may be retried on that server, or here
once it is settled, and nowhere else. Choose between the two with "Which
machine" in `references/placement-and-remote.md`, which also covers a machine
the user named earlier. A retry or a fresh start here carries
`--environment local`; one on a server carries `--on <server>` instead.

`--retry-of` names the newest failed attempt. Retry only after the cause
changes; the same start against an unchanged failure (an unreachable host)
fails the same way, so report it instead.

`worker-stop` exits 1 with `stop_unknown` when it cannot prove the agent
stopped; check `worker-show` before acting again.

`orchestration reset` deletes coordination state; run it only when the user
gives that state up.

## User-directed recovery after the breaker

After three failed starts in one `--retry-of` chain, the Dispatch circuit-breaks
and the Task fails. A worker's own failed report does not advance that count.
Report the failure and stop automatic retries; never route around the breaker
with a new Run or Task, or reset its count, including on restart.

Only when the user explicitly asks to retry or reassign this Task may its Run's
current coordinator reopen the **same Task**. Use `worker-list` above to find
every retained attempt, then inspect each:

```text
ORCA orchestration worker-show --dispatch <dispatch_id>
ORCA orchestration worker-read --dispatch <dispatch_id>
```

Silence, a startup timeout, or `unverifiable` liveness alone never proves exit or
authorizes autonomous stop, abandon, retry, or release.

For explicit user cancellation of an unsettled attempt, including an unknown
start, request `ORCA orchestration worker-stop --dispatch <dispatch_id>`.
Prior exit is not required: guarded stop can attempt cancellation of an exact
owned live agent or one with exact identity but unverifiable liveness. Respect
identity, custody, and Keep open refusals; never close or reuse an unknown or
user-owned process. Claim cancellation only on a confirmed stopped result. On
`stop_unknown`, inspect `worker-show` and the receipt, then report the unresolved
blocker; do not blindly repeat stop, retry, or start fresh.

For explicit intentional abandonment, use
`ORCA orchestration worker-abandon --dispatch <dispatch_id>` to fence and
settle the assignment while retaining possibly-live resources. This does not
cancel physical work or prove exit; never silently substitute it for cancellation.
A same-runtime in-flight stop must finish first. Reopen only after the Dispatch
is settled; never reuse an unproven or still-busy predecessor.

An already-failed start can still own a live terminal; stop/abandon does not close
it. For reclaimable failed-start terminals you are replacing, use
`ORCA orchestration worker-release --dispatch <dispatch_id>`; follow the
receipt's exact recovery action for `release_pending` or `release_unknown`, never
`terminal close`. Preserve the selected proven reusable agent with
`worker-keep-open` by its Dispatch ID; preserve user-taken-over and unproven
terminals. A fresh start without `--retry-of` does not clean up its
predecessor's terminal.

Reopen and start the same Task in its owning Run:

```text
ORCA orchestration task-update --id <task_id> --status ready --run <owning_run_id>
ORCA orchestration worker-start --task <task_id> --run <owning_run_id> --worktree <placement> --agent <agent>
```

This fresh series starts at zero. The broken Dispatch and its failure count stay
in history; `--retry-of` that Dispatch is still refused after reopening.

To reuse a proven existing agent whose previous work is settled, replace the
start command with:

```text
ORCA orchestration worker-start --task <task_id> --run <owning_run_id> --terminal <agent_terminal_handle>
```

It starts in that terminal's workspace; omit `--agent`, `--model`, `--effort`, and
new-worktree creation. Follow [Placement and remote execution](placement-and-remote.md)
for execution-host selection and Dispatch-addressed follow-ups. After starting
independent work, end your turn; Orca wakes you. Follow a receipt's `next` action.

# Worker teardown

A worker has three distinct endings: **settled** (attempt/Task outcome),
**ended** (dormant session), and **destroyed** (process proven gone). Keep Task
outcome, Dispatch attempt, and process/resource liveness separate. Silence, a
timeout, or `unverifiable` liveness supplies no proof of exit; a settled Task
can still have live or unverifiable resources.

## Settled: attempt and Task outcome

- `worker_done` settles the Dispatch and its Task: `succeeded` completes both,
  `failed` fails both. A reported failure is a conclusion; never mark it
  completed.
- If a terminal worker exits without reporting, Orca fails the Dispatch (the
  Task ordinarily returns to `ready`, or becomes `failed` at the circuit
  breaker) and mails the coordinator; a remote worker's stop relay carries the
  report home. A pending or unknown stop takes a separate path and can suppress
  the exit escalation.
- `exited` and `lost` are `stopReason` values; `unverifiable` is a liveness
  verdict. `exited` confirms process exit. `lost` is non-exhaustive - it can
  follow a deliberate pane close, restart recovery that cannot confirm exit or
  continuation (including a chat with no terminal), a failed start, or an
  app-server drop. The original agent may still be running: inspect
  `worker-show` before sending mail or retrying, and if liveness remains
  `unverifiable`, stop automatic recovery and report the uncertainty rather than
  launching a second agent.
- Three consecutive Dispatch failures in one `--retry-of` chain trip
  `circuit_broken` and fail the Task (a worker's own `worker_done --outcome
  failed` report does not advance that count); see
  [Recovery and cleanup](recovery-and-cleanup.md).

## Ended: the session is dormant, not destroyed

- An accepted report can arm automatic release when supported; auto-close runs
  only while the agent rests, while a working or needs-input agent keeps its
  terminal. `--keep-open` (or `worker-keep-open`) prevents automatic close.
  Auto-close and keep-open never change the Task's outcome.
- Records persist after close. A plain `send --to dispatch:<id>` (without
  `--on`) on local Orca or a paired server advertising
  `orchestration.remote-owned-workers.v1` can reuse an eligible open agent,
  reopen a resumable session, start fresh with prior context, or refuse when the
  workspace or restartable agent is missing; the receipt says what occurred.
- Only legacy paired-server attachments refuse `send` with `dispatch_inactive`;
  on that refusal, start new work there with `worker-start --on <server>`.

## Destroyed: the process is proven gone

- `worker-stop` settles an unsettled worker on confirmed stop or observed exit
  (a context-only `dispatch` is fenced with `processAction: none`). Otherwise
  it exits 1 with `stop_unknown` (which may coexist with
  `closed_agent_terminal`). A later observed exit or restart recovery can
  reconcile a pending stop; read the receipt and `worker-show` before acting
  again.
- `worker-release` performs post-completion cleanup for a settled worker and
  can also reclaim an eligible live terminal left by a failed start (which
  `worker-stop` / `worker-abandon` do not close), respecting custody and
  returning `retained` or `already_released` when no close is performed.
  `release_pending` exits 0 and recovery retries after inventory or reconnect.
  `release_unknown` exits 1: inspect `worker-show` and retry without
  `--retry-request` (a fresh request ID; reusing the ID replays the receipt),
  never with a broad `terminal close`.
- `worker-abandon` fences and settles the assignment while retaining
  possibly-live resources; it performs no process or filesystem action, refuses
  a same-runtime in-flight stop, and can leave the Task blocked.
- The settled-worker sweep releases only on a proven process exit; a live or
  unverifiable process keeps its terminal.

`ORCA orchestration worker-list --run <run_id> --include-remote` (paginated;
remote coverage is capability-dependent) reports each worker's liveness
(`live`, `exited`, `unverifiable`) and conditional `next` action; follow it.
